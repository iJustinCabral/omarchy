# EFI post-write hibernation marker experiment

This is a distinct, opt-in diagnostic module for the unchanged production kernel, not a hibernation fix or authorization to repeat a consumed S4 vector. It uses a new EFI variable `OmarchyT2PostwriteStage-47a2fceb-87bc-4e58-8d83-23f62ffb3393` containing efivarfs attributes `07 00 00 00`, magic `MBPW`, the first 12 bytes of a fresh 64-character vector, and one stage byte. The module neither creates nor deletes the variable. It loads disarmed, validates an exact prewritten stage-0 value when its root-only `arm_vector` parameter is set, and can be armed only once per insertion. Its ftrace hooks observe control flow without changing it.

Stage 1 is `hibernate()` entry. Stage 2 is `swsusp_write()` entry after snapshot creation. A return probe must observe `swsusp_write()` return zero before stage 3 can be reached by either `hibernation_platform_enter()` or `kernel_power_off()`; the two stage-3 hooks share one monotonic stage and cannot double-write. A nonzero write result, a completed `hibernate()` call, or a failed EFI write disarms the module, preventing a later ordinary shutdown from masquerading as S4 progress. Stage 4 is `acpi_hibernation_enter()` after the platform-stage hook. A stage-3 EFI value would distinguish an image-finalized source from an earlier source failure, subject to successful nonblocking EFI storage and independent returned-boot verification. It does not prove the hardware powered off, that the bootloader loaded the image, or that atomic or device restoration succeeded. The in-memory stage alone is not durable evidence.

The production kernel exposes all five target functions to ftrace. The pinned `hibernate.c` calls `power_down()` only after a successful `swsusp_write()` outside `test_resume`; shutdown mode enters `kernel_power_off()` and platform mode enters `hibernation_platform_enter()`. This ordering is a source-level contract for the installed 7.2.6 kernel, not a Mac hardware result. The extracted-C callback test covers out-of-order refusal, successful and failed image-write returns, stage 3's two equivalent hooks, monotonic stage 4, and failure disarming. Static checks cover the exact prewritten EFI identity gate and absence of flow redirection. Compile with the exact installed headers in a private build directory using `make -C /usr/lib/modules/$(uname -r)/build M=<private-build-dir> W=1 modules` after copying `Kbuild` and this C file.

`run-vm-postwrite` builds the module and a static init program for a disposable QEMU/OVMF guest using pinned production-kernel and firmware hashes. The guest writes stage 0, performs `disk=shutdown` with an isolated swap disk, and powers off. A separate cold guest boot reads the same OVMF variable and requires stage 3. The 2026-09-24 run passed with source log SHA-256 `35266a6ef912ff32470d66eea3da8ec4ad34eda0a3b24f827e3733ffda20445c` and return log SHA-256 `5ae54ea15de4b2832f959c4184bf7de8baeaa8e8703cecd4ba387b4acb65e92e`; durable copies are under `/home/jjc/.local/state/codex-mba-autonomous/postwrite-marker-vm/`. The guest did not attempt image restoration.
