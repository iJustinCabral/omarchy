# Pre-image-write boundary probe

This experimental external module redirects `swsusp_write()` at entry only while root explicitly arms it, returning `-ECANCELED` before it allocates swap pages or writes an image. Reaching the replacement means the stock `hibernate()` path has completed `hibernation_snapshot()` and returned to the source kernel. The stock error path then calls `swsusp_free()`, resumes tasks and returns a deliberate error instead of powering off. It does not test image writing, swap-header finalization or cold restore.

The module loads disarmed and refuses `armed=1` at insertion. A disarmed load/unload may validate the ftrace attachment without a PM transition. Do not arm it directly. `run-pre-write.py` is the single-use runner: it verifies the exact staged candidate, matching-stack prior `test_resume` proof, current-boot keyboard and trackpad evidence, root-owned module hash and vermagic, active services, and a normal read-only swap-header baseline at the exact resume offset. It records an independent permanent guard before arming and entering PM, then checks the single interception, deliberate error and unchanged swap-header page, restores radios and PM settings, and disarms its recovery timer only after cleanup. Its `--validate-only` path is read-only; the synthetic suite never enters PM.

The runner selects `test_resume`, not `shutdown`, because both use `hibernation_snapshot(false)` before `swsusp_write()`, while `test_resume` avoids ACPI S4 if the hook unexpectedly fails. A failed hook could still proceed into a full in-place image restore. The probe does not fix hibernation. The exact `.ko` remains root-owned mode 0600 in `/var/lib/codex-mba-pre-write-ftrace/`, with that directory root-owned mode 0700; it is unloaded on the current stock boot.

The sole armed run on v11 candidate boot `8727ce53-479c-46db-a4ee-4d7025e247f7` passed preflight and consumed `/var/lib/codex-mba-pre-write-ftrace/vectors/e81077476ec29e9aa6a2a110cf4514b915c6a9a8ea78a284761127b331af8800/pre-write-attempted`. It never returned to userspace or recorded an interception. The source journal ends at `PM: hibernation: hibernation entry`, the operator reported an unresponsive UI and spinning fans, and the stock return boot's swap-header page was unchanged. The hook might not have been reached, or its marker might have been lost when journaling stopped; the exact point of failure is unproven. This vector is terminal and must not be repeated. Its guard and attempt hashes are recorded in `docs/t2-suspend/HIBERNATION.md`.

The exact-entry `codex-mba-physical-input-pre-write.service` is a host-local monitor for the current v11 UKI hash. It records actual built-in keyboard and trackpad events into a new, root-owned evidence file on the candidate boot; a stock fallback boot exits without creating evidence. Do not reuse the earlier v11 input record from a different boot. Install and enable this unit only for the one-shot candidate diagnostic, and disable it after its result is reconciled.

## Distinct stock-kernel EFI boundary probe

`run-efi-boundary.py` defines a separate, one-use `test_resume` diagnostic on the unchanged production UKI and current stock driver stack. It prewrites a fresh vector-bound EFI stage 0, loads the existing hash-pinned EFI marker and pre-write abort modules disarmed, verifies both hooks are registered together, then arms them only after a root-owned `pm-attempted.json` guard has been fsynced. The EFI hook writes stage 1 at `hibernate()` entry and stage 2 at `swsusp_write()` entry; the IPMODIFY hook redirects `swsusp_write()` to `-ECANCELED` before any image write. A controlled return requires stage 2, exactly one interception, EFI status 0, unchanged swap-header page and restored PM controls. The runner preserves its marker and evidence even after a successful return; a hang requires physical power-off and return-boot inspection, never another attempt with the same vector.

On stock boot `7e684644-8756-423b-b509-5504c220dee7`, the exact existing modules (SHA-256 `28e13ee2a660c590d0d66988c0af9d768aa5a37e2e2ed52624215f624b149f32` and `ca1afffe28b16a41421ad6f0feb36fe5a7ad35dfb7bfb93ac95beb8882b551b6`) were loaded together disarmed. The live ftrace table showed one `hibernate` hook and both `swsusp_write` hooks, including the IPMODIFY flag; both modules then unloaded. No PM transition, EFI variable or boot image was changed by that compatibility check. This is a materially new boundary from the consumed v11 pre-write probe because it provides an EFI breadcrumb that can survive a forced power-off. It still cannot prove image writing, S4 entry, cold restore or working restored input.

That separate one-use vector then returned on the same stock boot. Its exact armed read-only gate passed after a narrow fix to allow only its prewritten stage-0 marker. The sole PM run detached Wi-Fi, powered down Bluetooth, created a snapshot, reached `swsusp_write()`, advanced the EFI marker to stage 2 with status 0 and intercepted the write once with deliberate `-ECANCELED`. The swap-header page was byte-identical before and after, PM controls were restored, Wi-Fi reconnected, Bluetooth was powered, no units failed, and both modules unloaded. Root-owned evidence lives under `/var/lib/omarchy-t2-efi-pre-write-boundary/`; `pm-attempted.json` is terminal. Keep the stage-2 EFI variable and all evidence until exact reconciliation. This localizes the current stock stack to a post-snapshot, pre-image-I/O boundary; it does not establish the v11 candidate path or usable S4.
