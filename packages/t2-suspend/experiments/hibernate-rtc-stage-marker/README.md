# Stock-kernel RTC stage marker experiment

This is an opt-in diagnostic module, not a hibernation fix, and it does not authorize an S4 attempt. It keeps the known-good production `.linux` section intact, unlike the rejected marker-kernel UKI that failed to mount `/dev/mapper/root`.

The pinned 7.2.6 kernel exports `generate_pm_trace()` and the live stock kernel exposes `hibernate`, `swsusp_write`, `hibernation_platform_enter`, and `acpi_hibernation_enter` to ftrace. This module loads disarmed and attaches only to those four functions. Setting its root-only `armed` parameter to `1` after loading writes a stage-0 RTC breadcrumb exactly once; inserting it with `armed=1` is refused. Later hooks advance monotonically through stage 1 (`hibernate` entry), stage 2 (`swsusp_write` entry after the source snapshot returns), stage 3 (`hibernation_platform_enter` after image writing returns successfully), and stage 4 (`acpi_hibernation_enter`). `stage` is read-only, and the module can be disarmed but cannot be rearmed without unloading it. No hook changes control flow or skips image I/O.

The RTC record uses the kernel's existing PM-trace format with a fixed file hash of `928`; the first field of the next boot's `PM: Magic number: user:file:device` is the stage. `marker.py --magic 2:928:0` or `marker.py --rtc-date 2048-05-13 --rtc-time 00:00:01` is a pure decoder for an observed record. A recognized hash is not tied to an attempt by itself: an eventual runner must capture the pre-arm RTC baseline, bind the module hash and stage to a unique root-owned attempt guard, verify the stage-0 readback, require `/sys/power/pm_trace` to remain disabled so generic device traces cannot overwrite this marker, and treat a missing or conflicting record as inconclusive. The final device-hash field is incidental. On a successful image restore, the in-memory stage may rewind to the snapshot value while the RTC retains the source-side later stage; the return audit must use the RTC and boot-bound guard rather than the module's restored counter.

`generate_pm_trace()` deliberately overwrites the hardware RTC time and sets the kernel's `pm_trace_rtc_abused` guard. The normal RTC driver then returns `EIO` on reads even if the hardware clock has been repaired. The stage-0 live check used `hwclock --directisa --show --utc --noadjfile` to read the raw CMOS date while the guard was set, then `hwclock --directisa --systohc --utc --noadjfile` to restore the hardware clock from the synchronized system time. Only after that, the module's root-only `rtc_repaired` parameter cleared the guard; its setter requires the module to be disarmed and verifies that raw CMOS time is valid and within 120 seconds of the system clock. Never clear the guard before repairing and verifying the hardware RTC. The PM-trace writer's RTC operation uses a spinlock and is used by kernel noirq tracing; the stage-0 check does not validate calling it from an ftrace callback during PM. The writer has no return status for RTC failure, so only a matching readback can prove a breadcrumb was stored. The module also does not provide an unattended reset: the host's iTCO watchdog remains disabled by firmware.

The 7.2.6 production-kernel module built with `W=1` (only the known pahole 1.31 versus 1.32 warning), attached/disarmed and unloaded on healthy stock boot `f7bfa4c9-3830-446b-ab88-3f4f11d1fe3e`. A separate stage-0-only arm wrote raw CMOS `2048-05-13 00:00:01`, decoded as exact marker `0:928:0`. The RTC was restored to `2026-09-23` UTC using direct ISA access; the guarded repair setter restored normal `/dev/rtc0`, `/sys/class/rtc/rtc0`, `hwclock`, and `timedatectl` reads. The module is unloaded, `/sys/power/pm_trace` remains `0`, and no hibernation or other PM transition ran. This validates stage-0 storage and cleanup only, not any of the four ftrace callbacks under PM.

Build against the exact running headers with `make KDIR=/usr/lib/modules/$(uname -r)/build W=1`; this only creates a private `.ko`. `make clean` removes compiler output. Do not arm it or run S4 merely because it compiles or passes the stage-0 check.

`boot_recovery.py` is the return-boot half of a future guarded attempt. It is inert without a root-owned `var/lib/omarchy-t2-hibernation-pair/rtc-active.json` naming an exact pair vector, source boot ID and module hash, plus the matching consumed `s4-attempted` guard and attempt JSON. On a different boot it captures the current kernel's early `PM: Magic number`, a direct-ISA RTC read and the decoded stage into new root-only evidence before any clock repair. A missing or conflicting marker remains inconclusive, not a successful stage. It waits for `NTPSynchronized=yes`, restores the hardware RTC from the synchronized system clock, verifies normal RTC time within 120 seconds, records a separate repair receipt and archives the active pointer. Restarting after a partial return preserves the first capture and resumes repair without overwriting evidence. The unit `codex-mba-rtc-return.service` retries only while a guarded active pointer exists; it does not arm PM or a boot entry.

The service and the two Python files were installed host-locally under `/etc/systemd/system` and `/usr/local/libexec/omarchy-t2-rtc-stage-marker` on stock boot `f7bfa4c9-3830-446b-ab88-3f4f11d1fe3e`. The unit is enabled but its manual start skipped because no active attempt exists. The repo runner does not create that pointer yet; the service is therefore not evidence that an S4 attempt is ready. No power transition ran during installation.
