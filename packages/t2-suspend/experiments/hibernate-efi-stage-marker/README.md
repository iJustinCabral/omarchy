# EFI source-stage marker experiment

`../0012-hibernate-efi-stage-marker.patch` adds an opt-in diagnostic to the pinned 7.2.6 kernel hibernation path. It is not a hibernation fix and is not installed or enabled by default. The `t2_hibernate_efi_marker` kernel parameter requires a pre-armed nonvolatile EFI variable before changing power state. The patch updates that variable once after `PM: hibernation: hibernation entry` and once after `hibernation_snapshot()` has returned to the source kernel but before `swsusp_write()` is entered. A failed read, wrong payload or EFI write aborts before image writing. The two successful values distinguish a failure before snapshot completion from a failure after snapshot completion; neither value proves that image writing began or completed.

The variable is named `OmarchyT2HibernateStage` under GUID `96234839-90c9-4cd5-97b2-7ba690f0af02`. Its data is 17 bytes: ASCII `MBA9`, twelve bytes reserved for a unique attempt identity, and a stage byte. Stage `0` is an exact pre-arm; stage `1` means the entry breadcrumb completed; stage `2` means the source snapshot returned and the second breadcrumb completed. EFI attributes must be nonvolatile, boot-service-access and runtime-access. Any future runner must bind the twelve identity bytes to its pair-wide guarded attempt, pre-arm and read back the exact bytes before entering PM, verify that no prior marker exists, and preserve the EFI variable for the return audit. It must not clear an old marker or any terminal guard to retry.

The patch applies cleanly to the retained `kernel-readback-input/linux-7.2.6` source with `git apply --check`. A disposable overlay of that exact source compiled `kernel/power/hibernate.o` with `make -j2 W=1 kernel/power/hibernate.o`; the resulting object SHA-256 was `7c3189bf00676ef0dd790ae44f3192929edd00d9cba58f39498c106a8aa7ba83`. This is a single-object compile, not a linked kernel, boot or firmware test. An EFI runtime write while userspace and kernel threads are frozen could itself block or fail, so an ordinary-boot read/write test of the exact EFI payload and a separate source-image build/boot audit are needed before considering a guarded hardware experiment. Even a validated marker would not supply an unattended reset: this MacBookAir9,1 reports that firmware disables `iTCO_wdt`, and there is no `/dev/watchdog`. Do not enable or execute this experiment until a recovery plan addresses that gap.
