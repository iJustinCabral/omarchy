# Stock-kernel EFI stage-marker prototype

This is an experimental marker, not a hibernation fix or authorization for another MacBookAir9,1 S4 attempt. Its distinct `hibernate()`-entry freezer vector has completed once on the stock MacBook; the S4 vector remains unqualified. It attaches disarmed ftrace callbacks to the production kernel's `hibernate()` and `swsusp_write()` entry points, leaving the production `.linux` and `.cmdline` sections untouched. A root-only arm parameter accepts the full lowercase pair vector only after the matching 17-byte stage-0 nonvolatile EFI variable has been prewritten and read back. The first hook attempts stage 1 at `hibernate()` entry; the second attempts stage 2 at `swsusp_write()` entry, after the source snapshot returned. The module does not create, delete or recycle an EFI variable, alter hibernation control flow, or arm a boot entry.

The callbacks use the pinned kernel's exported `efivar_trylock()` and `efivar_set_variable_locked(..., true)` path, also used by EFI pstore in crash contexts. An unavailable nonblocking variable or query service prevents arming. A failed stage write records the EFI status in RAM and disarms later writes, but cannot stop the in-progress hibernation; only a matching nonvolatile variable read on a later boot could prove a stage persisted. The pinned kernel's `vars.c` and `runtime-wrappers.c` show that "nonblocking" avoids sleeping on kernel locks but still invokes firmware `SetVariable` directly; it does not impose a firmware timeout. An ordinary boot/write/reboot/readback test and an independently proven cold-reset path are prerequisites to considering any S4 use. Firmware runtime calls can still hang, so compilation alone is not hardware qualification.

`persistence_probe.py` is a separate, one-use test protocol for a disposable `OmarchyT2EfiPersistenceProbe-0dc7b0e2-3b57-4e62-9159-caa993087e72` variable. It never touches the real S4 stage variable. It records a random exact value and source boot ID in new private state before an exclusive EFI write, requires a different boot ID for persistence verification, and permits cleanup only when the return-boot value exactly matches. A failed or mismatched probe is preserved, not retried or deleted. Live calls require an explicit opt-in plus stock boot, original production UKI/Limine hashes, no boot overrides, no loaded marker, disabled PM tracing, the consumed S4 guard, and a clean repository matching the handoff. The protocol has no command-line entry point.

The first live probe completed on source stock boot `ef1bc90d-7cce-4c1d-aea8-404e3b53c5b7`: full preflight passed, root-owned `armed.json` was fsynced before the 20-byte EFI write, and same-boot readback matched SHA-256 `14164d48881cf9dbf99d46995cc0a41070f9322c03accc45a8cbc82e48438757`. An ordinary stock reboot returned as `53dcba62-0eb1-4623-b5c7-68e343cdd689` on the primary encrypted Btrfs `@` root with original UKI/Limine hashes; cross-boot verification found the exact same EFI value and wrote `persisted=true` evidence. Exact-value cleanup cleared only the disposable variable and wrote `clear-intent.json` and `cleared.json`; the EFI variable is now absent, while all root-owned evidence remains under `/var/lib/omarchy-t2-efi-persistence-probe/`. The real S4 stage variable and marker module were absent throughout. This proves ordinary-reboot persistence for this variable, not survival of a forced power cut, a nonblocking in-kernel EFI write, or usable S4. The failed S4 vector is still terminal, and there is still no proven unattended reset path.

`kernel_probe.py` and the updated external module define the next, still-offline boundary. The module exposes a root-only, one-use `probe_nonce` parameter for a different prewritten `OmarchyT2KernelEfiProbe-d963eecc-8654-47d4-bc1c-456d7b776a86` variable. It verifies the exact 17-byte stage-0 value and uses the same `efivar_trylock()` plus `efivar_set_variable_locked(..., true)` helper as the S4 breadcrumb to write stage 1. Consuming this probe prohibits the module instance from arming S4, and consuming S4 arming prohibits the probe. Loading the module does not write EFI or enter PM. The userspace protocol fsyncs a root-owned arm record before prewriting stage 0, pins the private module hash and source version, checks a disarmed loaded module before the one-shot parameter write, records the returned EFI status and exact variable bytes, then requires a different stock boot before exact-value cleanup. Failures leave evidence and do not retry or delete a mismatched variable.

At that offline checkpoint the module had not been loaded and the second probe variable had not been created. Synthetic protocol and static safety tests passed, but no kernel-side EFI call or additional reboot had occurred. This path still does not prove firmware calls cannot hang in a frozen hibernation context or supply unattended reset.

The next offline-only `entry_probe.py` protocol targets the actual `hibernate()` ftrace callback with a third, distinct `OmarchyT2FtraceEntryProbe-9f946df0-1b9c-4af5-97e8-bc322a728241` variable. Its full stage-0 payload is `07 00 00 00`, `MBFE`, a random 12-byte nonce and stage `0`; the callback attempts stage `1` through the same nonblocking EFI helper at `hibernate()` entry, before processes freeze. The module's root-only one-use `entry_nonce` arm accepts only the exact prewritten nonce and excludes real S4 arming and the prior kernel-write probe in both directions. The runner fsyncs `pm-attempted.json` before invoking the hash-pinned `omarchy-debug-t2-hibernate test freezer --disk-mode shutdown --no-sudo-prompt --yes` helper. The pinned kernel's `TEST_FREEZER` branch returns before device suspend, image creation, `swsusp_write` or ACPI S4; `shutdown` disk mode skips platform S4 preparation. The helper restores PM controls if it returns. Synthetic tests verify guard-before-transition ordering, normal return, stale-variable refusal, and preserving stage evidence after a simulated hang. A different stock boot can capture the result; cleanup requires both an exact stage-1 marker and a successful source return. A failed or interrupted test is not retried.

The running stock kernel and production UKI were not changed, the revised module was not loaded, the third EFI variable was not created, and no freezer or S4 test ran. A successful future freezer test would qualify only that entry callback, not `swsusp_write`, cold image restoration, or unattended reset.

The live runner requires the boot-bound, root-owned operator-attended acceptance described in [the cold-power recovery gate](../../../../docs/t2-suspend/RECOVERY-GATE.md) before it can prewrite EFI stage 0, load the module or enter PM. The runner does not create that record automatically. Its acceptance for the completed freezer vector was boot-bound; it is not proof that manual recovery or firmware `SetVariable` is safe and does not authorize real S4.
