# In-place image-readback boundary

`mba_hibernate_readback_abort.c` is an external module for the unchanged production kernel. It registers an IPMODIFY ftrace hook on `hibernation_restore()` while disarmed. A separately guarded one-use arm redirects that call to `-ECANCELED` after `swsusp_read()` has returned but before device quiesce or atomic memory replacement. The hook consumes its arm once and reports an interception count. It is not a hibernation fix and must not be armed directly from the shell.

The pinned production `hibernate.c` calls `swsusp_check(false)` after writing a `test_resume` image, then `swsusp_read()`, closes the resume device and calls `hibernation_restore()` only on a successful read. `swsusp_check(false)` restores the normal swap signature before readback. A returned one-use abort would therefore distinguish completed image write/readback from the already-qualified pre-write boundary without exercising atomic restore. A write or readback hang still requires physical power-off, and a missed interception could execute the known-dangerous in-place restore path.

The production boot command line points at the existing `/swap/swapfile` physical page `1923214`. The pinned `find_hibernation_swap_type()` matches both block device and first swap extent offset, while the [kernel swap-suspend documentation](https://docs.kernel.org/power/swsusp.html) permits `/sys/power/resume_offset` to select a different active swap file for a source-side test. A separate temporary Btrfs swap file and verified offset could keep a failed diagnostic image away from the stock boot's original resume target. This isolation has not been qualified on hardware. Never change the active resume offset or create/activate a second swap area without a one-use runner that records the original state, verifies the alternate mapping and restores or inspects it after return. Do not use the old pre-write vector or clear its guard.

The module built with `W=1` against `7.2.6-arch2-Watanare-T2-2-t2` into SHA-256 `1d524ff4ca53980be38654f3f872fe3d82b725baac5fd6c9dbc86306db9aba39`, source version `7DCE0D2BAF567A1426BAD50`; only the known pahole 1.31/1.32 notice appeared. A root-owned 0700 directory and 0600 copy are at `/var/lib/omarchy-t2-readback-abort/`. On stock boot `7e684644-8756-423b-b509-5504c220dee7` the exact module loaded disarmed, exposed `armed=0` and `interceptions=0`, registered its `hibernation_restore` IPMODIFY hook and unloaded. No PM, EFI variable, swap area, resume offset or boot image changed in that check. The exact one-use image-I/O runner and its live recovery gates remain to be implemented and tested before any PM transition.

The disposable `run-vm-readback` harness boots the pinned production kernel in QEMU/OVMF with a fresh 4 GiB raw swap disk, the existing exact EFI stage module and the readback-abort module. Its DMI-guarded static init sets the guest resume device, arms a fresh EFI stage-0 vector and the abort hook, then runs `test_resume`. In the successful guest run, `/sys/power/state` returned `ECANCELED`, the EFI marker reached stage 2, the readback hook intercepted exactly once, and the swap header returned to `SWAPSPACE2`; the guest printed `MBA_VM_READBACK_RESULT=pass` and powered off. The retained console log SHA-256 is `b6b3c9cddb5fa8789dd9ffa1d0827440911cc52d77f452fb761b10292e55debe`; the sparse swap image contains 38 MiB of allocated blocks from image I/O. This proves the external hook sequence and normal-signature cleanup in the guest only. QEMU has no Apple T2, no encrypted Btrfs swap file and no physical built-in input, so the MacBook remains unqualified for a live image-I/O test.

`run-live-readback.py` is the separate, one-use Mac-side transaction. `--validate-only` is read-only. `--prepare` requires the exact stock boot, a clean repository matching the durable handoff, AC power, exact private modules, original active swap mapping and normal signature. It writes root-owned preparation evidence before creating a fixed 10 GiB temporary Btrfs swapfile under `/swap`, fsyncs the new file before reading its physical header, then records its distinct offset and header without changing runtime PM, EFI, active swap or boot configuration. On the first preparation attempt, the Btrfs swapfile header was still in delayed allocation immediately after creation, so the raw mapped page did not yet show `SWAPSPACE2`; the runner stopped before arming or PM, and a file sync made that exact page show the normal signature. `--recover-preparation` validates the retained intent and same boot, syncs the existing file and finishes that preparation without recreating the file or repeating a PM vector. The original intent pins an earlier clean checkpoint `6a465d16fc574e96bde67a7df34c64d80ba889b0`; recovery accepts that earlier head only when the retained intent's full SHA-256 is exactly `fb86cf4ad8664cb6258df33160d41bda2dd35c96336bb0b94cee11fcc889b1bf`. A failed preparation leaves its state and swapfile for inspection. `--validate-armed` checks the same boot, file ownership/size/mapping and intact headers without entering PM. No second vector can be prepared over the first.

`--execute --operator-attended` is a destructive-risk diagnostic, not an unattended hibernation fix. It fsyncs a terminal one-use guard before activating the separate swapfile, creates a fresh EFI stage-0 marker, loads and arms both exact modules, temporarily selects the alternate `/sys/power/resume_offset`, then uses the existing Wi-Fi/Bluetooth-isolating `test-resume` helper. On return it records the EFI stage, interception count, both swap headers and helper output, restores the original offset and unloads the modules. If PM was entered, the alternate swap stays active even when its signature is normal: the abort path may leave kernel-reserved hibernation slots that ordinary `swapoff` cannot release. A failed image signature also remains active and untouched for inspection. A forced power-off preserves the guard and EFI marker; the stock command line still names the original offset, so the next boot must use the stock entry and be reconciled before cleanup. The runner has a terminal guard even when setup fails, and never retries a consumed vector. Do not infer S4 or restored physical input from this source-side result.

For the consumed live vector `6701f3dfc5473a618c7b0411e650f1ea223b8d84c0eb3e0f4f351144763b90c8`, `cleanup-after-stock-reboot.py --mark-reboot-intent` checks the immutable source result, stock boot, both raw headers and exact EFI stage 2 before writing a durable ordinary-reboot intent. After an ordinary reboot to the same production entry and an updated reconciled handoff, `--validate-return` requires a different stock boot, the alternate file inactive and absent from `fstab`, unchanged raw headers and EFI value. `--record-return` writes that proof. Only then does `--cleanup-return` fsync an exact marker/file cleanup intent, clear that one EFI variable and remove that one inactive temporary swapfile, retaining all diagnostic evidence and a completion record. A failed check leaves state untouched. Never run this cleanup on the source boot or while alternate swap is active.
