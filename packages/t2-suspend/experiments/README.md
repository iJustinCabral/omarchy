# Hibernation diagnostic candidates

These patches are not part of `manifest.json`, normal source preparation, DKMS installation, or any automatic migration. They are diagnostic candidates, not qualified fixes. Do not install them over managed modules or bypass the boot-image source-version guard.

## BCE restore-entry abort

`0001-bce-abort-image-restore-probe.patch` applies to the prepared 1.4 BCE core source. Its read-only load-time parameter `hibernate_restore_abort` defaults to false. With it enabled, only the image `.restore` callback returns `-ECANCELED` before invoking `t2bce_resume`; ordinary suspend/resume and freeze/thaw retain their original callbacks. The diagnostic intentionally does not restore BCE, so internal input and audio may fail until reboot. It must not be presented as usable hibernation.

The purpose is to distinguish a reset before the BCE restore callback from a reset requiring its firmware handshake. A surviving kernel journal containing the explicit abort marker would show that low-level image restoration reached this boundary. Absence of a marker after another reset would not prove the callback was never reached. No repeated image test is authorized by compiling this patch alone: deployment must preserve the verified normal boot image, provenance, the source-version guard, and an unattended recovery path.

The exact wrapper is exercised by `python3 packages/t2-suspend/tests/test-bce-restore-probe.py <patched-t2bce_main.c>`. It verifies that default behavior forwards the resume result, opt-in abortion never invokes the firmware resume path, and the ordinary PM callback mapping is unchanged. The experimental module compiled with `W=1` against `7.2.6-arch2-Watanare-T2-2-t2`, yielding source version `6C39F3A7AEBE0C064C19344`. The build warned that pahole 1.31 differed from the kernel's 1.32, but completed. No hardware validation or installation has occurred.

The kernel's `scripts/Makefile.modinst` removes the destination's `kernel` and `build` paths during `modules_install`. Never run it against the production release. After the live build has exited successfully, verify `include/config/kernel.release` is exactly `7.2.6-arch2-mba-readback-t2`, then install first into a fresh staging directory with an explicit `INSTALL_MOD_PATH`. Inspect the resulting module tree, kernel image, symbol table and module ABI before copying only this new release into `/usr/lib/modules`; refuse an existing destination unless its contents and replacement are separately reviewed. Do not run `make install` or a production kernel package upgrade as part of this diagnostic.

The installed `omarchy-t2-radio/1.4` build script resolves headers via `/lib/modules/<release>/build`. Give only the new release a build link to the completed diagnostic tree, then build/install that DKMS version specifically for the new release. Verify the selected modules match that release's actual DKMS outputs. This preserves the normal initcpio provenance guard without fabricating DKMS artifacts or weakening its checks. Use a separate UKI output, verify its extracted command line, kernel and initramfs module provenance, and verify the production UKI's configured hash again before selecting a one-shot diagnostic boot. A successful build or boot is not proof of successful hibernation.

A subsequent source audit found an additional diagnostic cleanup requirement: normal successful restoration rewinds RAM to before image swap-slot allocation, whereas intentionally skipping restoration leaves those allocations live. The build was explicitly stopped before changing its inputs. Apply `0003-readback-probe-release-swap.patch` after `0002`; it releases the test image's recorded swap extents on every return from `load_image_and_restore`, including bitmap-allocation/read failures, only when both diagnostic opt-in and `test_resume` mode are selected. `swsusp_check(false)` has already restored the original swap signature before this function is reached. The expanded harness verifies slot release exactly once for each diagnostic exit and never for the normal path. This does not add new handling for an earlier `swsusp_check` I/O failure; deployment must treat an unexpected error as a failed diagnostic, not as proof that the image was safely consumed. Both patches are mandatory for the readback-only experiment.
