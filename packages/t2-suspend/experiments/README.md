# Hibernation diagnostic candidates

These patches are not part of `manifest.json`, normal source preparation, DKMS installation, or any automatic migration. They are diagnostic candidates, not qualified fixes. Do not install them over managed modules or bypass the boot-image source-version guard.

## BCE restore-entry abort

`0001-bce-abort-image-restore-probe.patch` applies to the prepared 1.4 BCE core source. Its read-only load-time parameter `hibernate_restore_abort` defaults to false. With it enabled, only the image `.restore` callback returns `-ECANCELED` before invoking `t2bce_resume`; ordinary suspend/resume and freeze/thaw retain their original callbacks. The diagnostic intentionally does not restore BCE, so internal input and audio may fail until reboot. It must not be presented as usable hibernation.

The purpose is to distinguish a reset before the BCE restore callback from a reset requiring its firmware handshake. A surviving kernel journal containing the explicit abort marker would show that low-level image restoration reached this boundary. Absence of a marker after another reset would not prove the callback was never reached. No repeated image test is authorized by compiling this patch alone: deployment must preserve the verified normal boot image, provenance, the source-version guard, and an unattended recovery path.

The exact wrapper is exercised by `python3 packages/t2-suspend/tests/test-bce-restore-probe.py <patched-t2bce_main.c>`. It verifies that default behavior forwards the resume result, opt-in abortion never invokes the firmware resume path, and the ordinary PM callback mapping is unchanged. The experimental module compiled with `W=1` against `7.2.6-arch2-Watanare-T2-2-t2`, yielding source version `6C39F3A7AEBE0C064C19344`. The build warned that pahole 1.31 differed from the kernel's 1.32, but completed. No hardware validation or installation has occurred.

### Build-scope correction

On September 20, after more than 84 minutes of full-distribution compilation and operator concern about duration, the healthy build invocation `055fd69220094f94bc019f444ef0ea58` was deliberately stopped (inactive, MainPID 0, no remaining compiler processes). PCI enumeration showed only Intel Ice Lake graphics `8086:8a5c`. The host diagnostic configuration now disables `DRM_AMDGPU`, `DRM_RADEON`, `DRM_NOUVEAU`, and `DRM_XE`, retaining `DRM_I915`. `olddefconfig` also removed their dependent options, including `PM_GENERIC_DOMAINS` and `PM_GENERIC_DOMAINS_SLEEP`; this is a configuration difference to account for in interpreting future results, not an identical-config reproduction. The original configuration is retained at `kernel-readback-input/config.before-gpu-prune`; `scripts/diffconfig` against it reproduces the complete difference. New configuration SHA-256 is `52d28e1978d7b86299c371f565d9740f3335e385fe9b1fbb14092b582a00a5d4`. The same build tree resumed without cleaning under invocation `fa083e210d2e4ad7b4e73c9f4625760b`. Production modules and boot images remain untouched; no new hardware test has run.

After creation-only also passed with PM trace enabled (see `docs/t2-suspend/HIBERNATION.md`), `0002-hibernate-readback-probe.patch` adds an opt-in `hibernate_readback_probe=1` boot parameter. In `test_resume` mode only, a successful `swsusp_read` is followed by a diagnostic marker and `-ECANCELED`, before `hibernation_restore` can quiesce devices or replace memory. The existing image/bitmap cleanup and process-thaw paths remain in use. This deliberately rejected transition is not successful hibernation. An intact readback marker would qualify the write/readback boundary, including the reader's integrity checks; no marker after reset would remain inconclusive. The ordinary boot resume path and other hibernation modes are unchanged by this flag. No live test of this patch has occurred.

`python3 packages/t2-suspend/tests/test-readback-probe.py <patched-kernel/power/hibernate.c>` compiles the actual modified function into a syscall-free harness. It covers opt-in parsing, flag/mode combinations, allocation and read errors, close/free/unlock behavior, and exclusion of restoration only after successful diagnostic readback. This passed on the prepared source. Kernel compilation remains a separate requirement.

The host-local build tree is `/home/jjc/.local/state/codex-mba-autonomous/kernel-readback-input/linux-7.2.6`. Its inputs reproduce the running package's [recipe](https://github.com/NoaHimesaka1873/linux-t2-arch/blob/adfecd72ae4333a08b9f574d5b75370d06524491/PKGBUILD): Linux 7.2.6 tarball SHA-256 `039aef84f2b0994aeda3f4fcfc3d02ec9d7a9bbb9020ea264c43f446c860f606`, Arch patch SHA-256 `366b1efc1a4fa6e39713ae89e006d99b9f790682358b8bc84c784754a9d70b94`, and T2 patches at `794069f7015e25d62da420e2748daaac0813cedc`. Both downloaded hashes matched before extraction/application. All patches applied with fuzz disabled. The installed 1.4 prepared brcm80211 source, BCM4377 source and BCE core source overlay the kernel tree to retain the current driver behavior; the earlier BCE restore-abort patch is not included. Comparing T2 patch revisions `794069f` and `fea0074` found only gmux/APFS changes, no BCE difference; do not assume a newer package fixes this failure.

The installed kernel configuration was copied and refreshed with `olddefconfig`. Missing `rust-src` and `rust-bindgen` build dependencies were installed through the package helper to avoid silently disabling Rust features. The resulting configuration differs only in tool version metadata: pahole 1.31 versus 1.32 and bindgen 0.73.1 versus 0.73.2. The separate release is `7.2.6-arch2-mba-readback-t2`, with no changes to installed module directories, production boot image or default entry. Build with `make -j3 bzImage modules` in the prepared tree; the host build is tracked by user unit `mba-kernel-readback-build.service`. Do not reboot or start a hardware PM test while it is running. Before deployment, inspect build status, verify module/source provenance and ABI, and stage a separate one-shot image with a verified production recovery entry; do not install over the normal kernel.

The first build invocation exited 2 during `include/generated/timeconst.h` generation because `bc` was missing. After confirming its terminal state, `bc` was installed through the package helper and all non-documentation recipe dependencies were checked as installed. The same build tree resumed under the same user unit, invocation `48e78599babd4d509785f0bc29596986`, and progressed through Rust bindings/core compilation. This is build progress only, not a completed kernel or hardware result.

A subsequent source audit found an additional diagnostic cleanup requirement: normal successful restoration rewinds RAM to before image swap-slot allocation, whereas intentionally skipping restoration leaves those allocations live. The build was explicitly stopped before changing its inputs. Apply `0003-readback-probe-release-swap.patch` after `0002`; it releases the test image's recorded swap extents on every return from `load_image_and_restore`, including bitmap-allocation/read failures, only when both diagnostic opt-in and `test_resume` mode are selected. `swsusp_check(false)` has already restored the original swap signature before this function is reached. The expanded harness verifies slot release exactly once for each diagnostic exit and never for the normal path. This does not add new handling for an earlier `swsusp_check` I/O failure; deployment must treat an unexpected error as a failed diagnostic, not as proof that the image was safely consumed. Both patches are mandatory for the readback-only experiment.
