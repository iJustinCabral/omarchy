# Hibernation diagnostic candidates

These patches are not part of `manifest.json`, normal source preparation, DKMS installation, or any automatic migration. They are diagnostic candidates, not qualified fixes. Do not install them over managed modules or bypass the boot-image source-version guard.

## BCE restore-entry abort

`0001-bce-abort-image-restore-probe.patch` applies to the prepared 1.4 BCE core source. Its read-only load-time parameter `hibernate_restore_abort` defaults to false. With it enabled, only the image `.restore` callback returns `-ECANCELED` before invoking `t2bce_resume`; ordinary suspend/resume and freeze/thaw retain their original callbacks. The diagnostic intentionally does not restore BCE, so internal input and audio may fail until reboot. It must not be presented as usable hibernation.

The purpose is to distinguish a reset before the BCE restore callback from a reset requiring its firmware handshake. A surviving kernel journal containing the explicit abort marker would show that low-level image restoration reached this boundary. Absence of a marker after another reset would not prove the callback was never reached. No repeated image test is authorized by compiling this patch alone: deployment must preserve the verified normal boot image, provenance, the source-version guard, and an unattended recovery path.

The exact wrapper is exercised by `python3 packages/t2-suspend/tests/test-bce-restore-probe.py <patched-t2bce_main.c>`. It verifies that default behavior forwards the resume result, opt-in abortion never invokes the firmware resume path, and the ordinary PM callback mapping is unchanged. The experimental module compiled with `W=1` against `7.2.6-arch2-Watanare-T2-2-t2`, yielding source version `6C39F3A7AEBE0C064C19344`. The build warned that pahole 1.31 differed from the kernel's 1.32, but completed. No hardware validation or installation has occurred.

## Restore-image DMA-quiesce candidate

After the sixth guarded boundary completed temporary page-table construction and restore-code relocation, the unresolved reset was confined to `restore_image()` or the restored execution it enters. ## Cold-S4 BCE queue reconstruction candidate

`0006-t2bce-rebuild-queues-for-hibernation.patch` applies after experiment 0005 and addresses a separate stale-transport problem. The current no-state path removes and later re-adds the virtual HCD while retaining the BCE command, VHCI message/event and audio queue objects. Those objects contain DMA mappings and producer/consumer state from the pre-hibernation bridgeOS epoch and cannot be assumed valid after cold S4.

The candidate forces `.freeze` and `.poweroff` through the no-state protocol and captures a transport-absent snapshot. After `SLEEP_NO_STATE` succeeds, it synchronizes the DMA IRQ and locally destroys the client queue graphs before the core command queues, without sending unregister commands to sleeping firmware. Thaw and restore perform a new firmware-version handshake, recreate command queues and then invoke every client's queue-rebuild callback. VHCI recreates message queues before event queues and re-adds its HCD only during successful completion. Audio recreates its BCE queue graph, waits for the remote endpoint, bounds-checks and revalidates the firmware BufferStruct mapping, and only then restores remote access. A loaded BCE client without the complete callback set makes the transition fail before queue destruction.

Real S4 may cold-boot bridgeOS, so only `.restore` may fall back from a failed `RESTORE_NO_STATE` request to the probe-time new-epoch handshake. Ordinary S3 resume and hibernation unwind cannot use that fallback. Rebuild failure tears down the partial graph, latches the failure and suppresses client completion.

The validation base was recreated from the post-0005 source plus the pinned package-1.5 audio hibernation callback patch; the regression test requires those `.freeze`, `.thaw` and `.restore` mappings so an older audit snapshot cannot qualify accidentally. The patch applies with fuzz disabled and the applied source exactly matches the reviewed candidate. `python3 packages/t2-suspend/tests/test-cold-s4-rebuild.py <patched-source>` compiles the extracted core path and exercises the forced ordering, unsupported-client rejection, sleep failure, normal no-state reconstruction, restore-only cold fallback, rebuild rollback and unchanged stateful S3 path. It also models the complete two-pass image lifecycle: the first freeze captures a queue-absent snapshot, the source-kernel thaw rebuilds queues, the image-loading quiesce drops them again, and atomic restoration rewinds to the original queue-absent state before `.restore` reconstructs it. The DMA harness independently models the matching pair of noirq gates and verifies that both the live PCI commands and the rewound PCI saved states remain bus-master-disabled until ordinary restore. The complete BCE module set builds with `W=1` against `7.2.6-arch2-Watanare-T2-2-t2`; the core, VHCI and audio module SHA-256 values are `4509db2ae82116817b076f066ce5db2ff72e06ca5852c068c52fbeac4bb49972`, `bd2598fd39c01b5e5c9782df214ce7535320eb5ab8d4cc54302e266b771c5eb0` and `4ddd16444e814fe07b470369fe3b83554fc1f328a502d374f8fe11093f14be8d`. Rollback likewise refuses unknown content and refuses to run while a one-shot request still exists.

Limine publishes `LoaderEntries` while constructing its menu, so a newly staged entry is not eligible to arm during the same running boot. The `arm` action therefore requires a separate successful production boot after staging and verifies that Limine advertised the exact `MBA-T2-hibernation-candidate` identifier. It then records the `arming` receipt, synchronizes storage, and makes `bootctl set-oneshot` its final mutation. The only following operation reads back the EFI variable and verifies the exact identifier.

The locally audited Limine v12.8.0 source at commit `89644f19a2d95c589494997ecb8a14b0a7429f05` deletes `LoaderEntryOneShot` before resolving the requested menu entry. If the candidate starts and then hard-locks, a forced power cycle cannot select it a second time; the next boot falls through to the unchanged production `default_entry: 2`. A missing candidate entry also falls through to that default after consuming the request. This removes the prior requirement to manually choose stock after each unusable experimental boot, although the platform still has no working watchdog capable of performing the cold power cycle itself.

`python3 packages/t2-suspend/tests/test-hibernation-candidate-boot.py` exercises transactional staging, pre-refresh arm refusal, exact advertised-entry gating, sync-before-arm ordering, one-shot readback, rollback refusal while armed, simulated one-shot consumption and exact production restoration. A future hardware sequence must first qualify an ordinary boot of the candidate without hibernating. Only a separate later one-shot boot may attempt hibernation. Neither step is authorized merely by this offline test; staging, arming, rebooting and power-state transitions still require explicit operator approval.
