# Hibernation diagnostic candidates

These patches are not part of `manifest.json`, normal source preparation, DKMS installation, or any automatic migration. They are diagnostic candidates, not qualified fixes. Do not install them over managed modules or bypass the boot-image source-version guard.

## VHCI command timeout quarantine

The v9 successful `test_resume` journal contains 25 VHCI cancellation-timeout warnings during virtual USB teardown. This does not establish the cause of the later cold-S4 or v11 source failures, but source review found a definite waiter-lifetime bug: if a timed-out command cannot reserve a cancellation slot, the old code returns with `completion.result` still pointing to its caller's stack. Patch `0013-t2bce-quarantine-vhci-command-timeout.patch` clears that pointer under the completion lock and quarantines the queue after a failed cancellation reservation, an unacknowledged cancellation or a mismatched reply. Subsequent commands fail until the no-state rebuild creates a new queue; normal successful commands remain unchanged.

The candidate verifier applies this patch after experiment 0011. Its extracted-C fault harness exercises a late reply after the failed-reservation return, retries on the quarantined queue, cancellation timeout, mismatched reply and normal success. Full pinned-source reconstruction, candidate regressions and all ten `W=1` module builds passed for 7.2.6; the private output remains outside `/boot` with `installed=false` and `hardware_qualified=false`. This is an offline memory-safety repair and a new candidate identity, not evidence of working hibernation or permission to replay a consumed test.

Patch `0014-t2bce-remove-vhci-before-hibernate-queue-pause.patch` addresses the ordering that makes the observed cancellation timeouts plausible. The old forced no-state path pauses `ev_system`, which delivers VHCI command replies, before `usb_remove_hcd()` sends teardown commands; the changed path removes the HCD with that queue still live and only then pauses event queues. A failed capability check refuses before removal, and later failures use the existing client abort path. The cold-S4 extracted-C harness checks this ordering, refusal and unwind; full pinned reconstruction and ten-module `W=1` build passed. It changes the experimental BCE core, not the managed production driver, and has no Mac PM qualification.

## BCE restore-entry abort

`0001-bce-abort-image-restore-probe.patch` applies to the prepared 1.4 BCE core source. Its read-only load-time parameter `hibernate_restore_abort` defaults to false. With it enabled, only the image `.restore` callback returns `-ECANCELED` before invoking `t2bce_resume`; ordinary suspend/resume and freeze/thaw retain their original callbacks. The diagnostic intentionally does not restore BCE, so internal input and audio may fail until reboot. It must not be presented as usable hibernation.

The purpose is to distinguish a reset before the BCE restore callback from a reset requiring its firmware handshake. A surviving kernel journal containing the explicit abort marker would show that low-level image restoration reached this boundary. Absence of a marker after another reset would not prove the callback was never reached. No repeated image test is authorized by compiling this patch alone: deployment must preserve the verified normal boot image, provenance, the source-version guard, and an unattended recovery path.

The exact wrapper is exercised by `python3 packages/t2-suspend/tests/test-bce-restore-probe.py <patched-t2bce_main.c>`. It verifies that default behavior forwards the resume result, opt-in abortion never invokes the firmware resume path, and the ordinary PM callback mapping is unchanged. The experimental module compiled with `W=1` against `7.2.6-arch2-Watanare-T2-2-t2`, yielding source version `6C39F3A7AEBE0C064C19344`. The build warned that pahole 1.31 differed from the kernel's 1.32, but completed. No hardware validation or installation has occurred.

The early callback first reads all four shared T2 PCI functions and refuses to wake firmware unless ANS, BCE, SEP and audio remain bus-master-disabled. A timeout, busy mailbox, malformed reply or unexpected DMA enable is recorded and propagated. Restore-only cold-epoch fallback remains available after a failed early wake; normal resume and thaw still fail closed. The extracted-C harness covers the inactive gate, DMA-enabled refusal before any mailbox write, successful wake, duplicate suppression, wrong reply type, timeout and busy mailbox. The patch also builds all ten radio and BCE modules with `W=1`; the only warning is the existing pahole 1.31 versus kernel-build 1.32 mismatch. The resulting `t2bce_core.ko` has SHA-256 `4a3e75b678f7e0560357667f37b61f7710cb237c02c16cb41a8fa0b00cf513f8` and source version `A8841C11E545290E509AD04`. This is a materially new transition vector and does not authorize reuse of the consumed v7 or v8 images.

## Recovery-safe candidate boot staging

`stage-hibernation-candidate-boot.py` implements the reviewed recovery design as separate `stage`, `verify`, `arm` and `rollback` actions. Staging requires the healthy production entry to be selected, an exact production UKI match with the private candidate's provenance, one unambiguous `default_entry: 2`, a current BLAKE2b hash for the production Limine path and no persistent or one-shot EFI override. It copies the candidate to its own ESP pathname and appends one managed Limine entry while leaving production as the explicit default. It does not arm or request a reboot.

The stage operation journals the exact original and proposed hashes before changing the ESP. Every file replacement is atomic and directory-synchronized. If any write after journaling fails, it restores the owned Limine configuration, removes only an exact-hash candidate image and records the recovered failure. The synthetic test injects failures after each of the five transaction writes and proves that production is restored. Rollback likewise refuses unknown content and refuses to run while a one-shot request still exists. Its `rolling-back` receipt makes each removal step retryable after an interruption, including after the original Limine configuration or candidate-image deletion has already completed.

Limine publishes `LoaderEntries` while constructing its menu, so a newly staged entry is not eligible to arm during the same running boot. The `arm` action therefore requires a separate successful production boot after staging and verifies that Limine advertised the exact `MBA-T2-hibernation-candidate-<UKI-SHA256-prefix>` identifier recorded in the receipt. Binding the identifier to the image hash prevents a stale or colliding generic menu name from selecting another artifact. The action then records the `arming` receipt, synchronizes storage, and makes `bootctl set-oneshot` its final mutation. The only following operation reads back the EFI variable and verifies the exact identifier.

The locally audited Limine v12.8.0 source at commit `89644f19a2d95c589494997ecb8a14b0a7429f05` deletes `LoaderEntryOneShot` before resolving the requested menu entry. If the candidate starts and then hard-locks, a forced power cycle cannot select it a second time; the next boot falls through to the unchanged production `default_entry: 2`. A missing candidate entry also falls through to that default after consuming the request. This removes the prior requirement to manually choose stock after each unusable experimental boot, although the platform still has no working watchdog capable of performing the cold power cycle itself.

`python3 packages/t2-suspend/tests/test-hibernation-candidate-boot.py` exercises transactional staging, hash-bound entry identity, pre-refresh arm refusal, exact advertised-entry gating, sync-before-arm ordering, one-shot readback, rollback refusal while armed, simulated one-shot consumption, interrupted rollback at every write boundary and exact production restoration. A future hardware sequence must first qualify an ordinary boot of the candidate without hibernating. Only a separate later one-shot boot may attempt hibernation. Neither step is authorized merely by this offline test; staging, arming, rebooting and power-state transitions still require explicit operator approval.

After that separately authorized boot-only step, `verify-hibernation-candidate-boot.py --candidate-source <private-UKI-directory>` provides a read-only machine check. It requires the one-shot request to have been consumed, the hash-bound Limine entry to be selected, the exact candidate UKI provenance, kernel release and command line, candidate source versions for every model-required loaded module, exact MacBookAir9,1 PCI identities and bindings, and registered Wi-Fi, Bluetooth, BCE keyboard/trackpad and T2 audio interfaces. For the post-`switch_root` policy it additionally requires a boot- and entry-bound loader marker whose source versions match provenance, proving that an ordinary candidate boot used the isolated payload rather than an installed module. Its result deliberately leaves `physical_input_confirmed`, `hibernate_attempted` and `hardware_qualified` false: device registration cannot substitute for the operator confirming that the keyboard and trackpad actually respond, and boot-only success cannot qualify hibernation.

`run-hibernation-candidate-test.py` is the single-use `test_resume` runner for a candidate that passes that boot-only check. `--validate-only` is read-only and additionally verifies the kernel hibernation controls, one active swap file, resume device and offset, globally serialized PM, no prior guard for the exact candidate UKI hash and no pending Wi-Fi cleanup. `--execute --physical-input-confirmed` is deliberately separate: it powers Bluetooth down, invokes the owned Wi-Fi detach helper, selects `test_resume`, enables PM trace, and arms a five-minute systemd recovery reboot timer. The vector-specific per-boot attempt JSON and guard survive a reset and prohibit repeating that candidate transition while allowing a materially different candidate to use a new vector.

The runner retains compatibility with the original fixed guard by resolving its boot ID to the matching legacy attempt JSON. A different candidate is eligible only for its own full-hash vector directory; the legacy guard is never cleared or repurposed.
