# Repeatable hibernation integration

This directory contains an offline-tested integration and explicit host backend, not an installed hibernation service. The first v16 experiment restored the original source session successfully; its consumed test vector remains immutable. See [hardware evidence](../../../docs/t2-suspend/HIBERNATION.md).

`transaction.py` models a separate product-cycle ledger using explicitly supplied directories. It has no CLI, EFI operations, module loading, power transitions or imports of the historical experimental runner. Synthetic tests exercise it in temporary directories. No actual MacBookAir9,1 product qualification is supplied or created.

The immutable image-pair qualification identity and each fresh cycle identity serve different purposes. Cycle identities include a UUID, original boot, artifact manifest and external qualification binding; new identities cannot bypass an active, failed or unreconciled predecessor. Changes to the manifest invalidate qualification. Consumed historical test guards must never be deleted, reclassified or worked around by changing an image hash.

Qualification, return and archive receipts are external attestations in this initial ledger, not independently authenticated hardware proof. Metadata archival does not itself copy or authenticate raw EFI originals. A future adapter must validate and durably preserve those originals before reporting archival, verify original-source continuity and cleanup before reporting return/reconciliation, and implement narrowly owned reusable-slot retirement. The ledger performs none of these operations and cannot authorize a physical test.

`continuity.py` adds an injected, original-process collector: it validates consumed cycle records before its one power-write callback, retains a nonce and immutable pins, captures raw EFI immediately on return, and verifies cleanup health before proposing an internally hashed return record. There is no built-in power operation or host sampler. Its proof is conditional on a trusted original process and correctly implemented callbacks, not authentication of arbitrary JSON or caller-supplied provenance. An ordinary boot, historical experiment proof, changed process or mismatched cycle cannot substitute for that return path. Physical input and usable-hibernation qualification stay false.

`evidence_archive.py` copies explicitly supplied raw bytes into a private exclusive archive, verifies them, and durably publishes a completion manifest binding the cycle, return receipt and each member's size/hash. It never reads live EFI paths, retires slots or deletes evidence. Partial archives fail closed and remain preserved. This establishes copy integrity, not the truth of observations supplied by the caller.

`workflow.py` connects the retained collector to the ledger under one lock, checks the exact prepared cycle and qualification, journals raw observations before cleanup, computes the witness digest itself and verifies the byte archive before marking the cycle archived. Cleanup runs on injected write/capture failures too; interrupted persistence leaves an incomplete or blocked cycle, and the same collector cannot retry. This adapter stops at archived: no reusable-slot release, reconciliation or next-cycle authorization is supplied.

`artifacts.py` derives structural pins from explicitly supplied source, restore and production images using the existing pair audit and source-layout checks. The ledger manifest and separately hashed audit details bind the actual image/provenance bytes, production sections, module identities and resume policy. Structural evidence does not create product qualification; the external source-marker module still requires its own checked pin. This adapter is read-only apart from temporary extraction files.

Artifact reads and comparisons stream in 1 MiB chunks; only small metadata/text inputs use bounded reads. Initial whole-image buffering reached roughly 4.9 GB RSS on the 8 GB development machine and was stopped without a power transition. The corrected real-image audit passed under a 1.5 GiB address-space limit, with Python peak RSS 24,036 KiB and child peak RSS 56,300 KiB. Its exact v16 audited-details digest is `593ce958a07f36510ed5722863b90f43ac20e567e6db798a62586d85f2177d91`; source/restore/runtime and production section hashes match the recorded successful pair. Sparse-file tests reject regressions to unbounded artifact reads. This is structural audit evidence, not product qualification.

`host_observation.py` supplies a read-only sampler with explicit filesystem roots and query callbacks. It joins the artifact report to actual source image/provenance bytes, embedded early-source module selections, loaded module identities and a separately pinned source marker. It samples raw EFI, consumed records, power settings and cleanup health. Partial read failures remain available to the collector and durable failure journal but cannot establish success. Post-cleanup checks reject restore-only and abort modules. Report digests establish consistency, not producer authentication; the caller must retain the trusted artifact audit. There is no default live backend or qualification creation.

`slot_retirement.py` verifies the archived product-cycle bytes before invoking injected compare-and-delete callbacks for exactly the fixed V3 source and V2 restore stage slots. It preflights both slots, journals confirmed absence, rechecks archive integrity and health, and computes release/reconciliation receipts internally. Vector witnesses, consumed guards and historical experiments are outside its scope. No live EFI backend is supplied, and this adapter does not authorize clearing the successful historical v16 markers.

A durable unresolved-retirement sentinel precedes deletion and blocks new cycle allocation even if reconciliation publication and all subsequent failure writes fail. It is removed only after reconciliation is durable. Allocation also verifies the terminal retirement receipt chain; a surviving sentinel fails closed. A sentinel-cleanup error after durable reconciliation is reported separately and is not a new hardware result.

`preparation.py` implements the successful runner's preparation and cleanup order through an explicit backend: stop active bolt, power down Bluetooth if previously powered, detach owned Wi-Fi, select the qualified PM baseline, persist a consumed product guard, load and arm the pinned source marker, write exact stage-zero slots, and arm the restore one-shot. It records each action before invoking it, verifies readbacks and publishes a preparation receipt bound to the ledger. Cleanup restores only owned changes, preserves all stage evidence and guards, and still attempts recovery if a cleanup journal write fails. It never writes the hibernation power-state trigger itself.

The sampler accepts an armed restore one-shot only when the completed preparation receipt hashes to the cycle's ledger receipt and names that exact entry and boot. A later cycle may accept restore-entry selection only through the immediately preceding reconciled product cycle, its actual byte archive and retirement chain, with the same original boot and artifact qualification. Immutable allocation links and a private head establish ordering without timestamps; missing or interrupted chronology fails closed. An ordinary restore boot or historical experiment record is not a substitute.

The existing fullrestore initramfs reads the cycle prefix from the stage-zero EFI marker; it does not embed the experimental pair vector. This permits the same audited image to consume a fresh product cycle without rebuilding it. The historical runner's text guard format and one-use staging state remain unchanged and cannot be reused as the product backend.

`host_backend.py` supplies the fixed host operations used by preparation, observation, the one-use power callback and archive-authorized retirement. Live operation requires an explicit `/` root and root identity, disallows injected command/sysfs implementations, and uses fixed command allowlists and a deterministic environment. Power and retirement callbacks require an active scoped ledger capability. EFI retirement additionally relies on the dispatcher's global serialization and absence of marker writers; efivarfs does not offer a native compare-and-delete primitive. Synthetic backends cannot establish hardware qualification.

Loader variables are checked individually: the owned one-shot uses nonvolatile attributes `0x07`, matching [bootctl's setter](https://github.com/systemd/systemd/blob/main/src/bootctl/bootctl-set-efivar.c) and [systemd's EFI writer](https://github.com/systemd/systemd/blob/main/src/basic/efivars.c), while the selected-entry witness uses `0x06`. Fixture coverage rejects the earlier incorrect volatile one-shot framing. Readiness allows zram alongside exactly the audited disk swapfile, whose actual Btrfs mapping must match the resume device and offset.

`trial.py`, exposed through hidden `omarchy debug t2-hibernate-trial [inspect|check|execute]`, wires those operations for an explicitly authorized one-use product trial. Default inspection and checks perform no preparation or power operation. The live command uses fixed pre-provisioned root-private state under `/var/lib/omarchy/t2-hibernate-trial`, a global physical-cycle lock and a permanent consumed trial guard; there are no alternate-root, force or skip-validation CLI flags. It verifies actual staged images, production fallback, entry mapping, source readiness and the boot-bound authorization before consuming permission. Deployment is rechecked immediately before the power write. Execute requires an explicit root invocation and never prompts or escalates automatically.

Trial authorization has its own protocol and `qualified=false`, including the exact artifact audit and external marker pins. Recovery attendance is an explicit boot-bound attestation, not physical-input qualification or a request to repeat keyboard/trackpad tests. The trial permits one cycle only, even after success; it cannot be replayed through a new UUID or a copied authorization in another ledger sharing the fixed live guard. The existing `qualification_sha256` cycle field binds the applicable authority receipt and does not promote trial permission into product qualification.

Neither source development nor these tests provision live configuration, issue authorization or install a service. The repository's normal hibernate menu now routes through `omarchy-system-hibernate`, but this wiring does not activate the product path. The earlier experimental v16 proof is not silently relabeled as product qualification.

The remaining integration must connect the tested early-source and isolated-restore boot policies with safe normal desktop hibernation, artifact deployment and update invalidation, and failure recovery. Do not enable it on the strength of this library or a single experimental return. Preserve production kernel/command-line bytes and the cold guard's ANS completion, DMA ownership and terminal pending-resume protections.

## Routine command and service deployment boundary

Without `/etc/omarchy/t2-hibernate-product.enabled`, `omarchy system hibernate` retains the existing `systemctl hibernate` behavior. Marker presence selects a fail-closed route: it must be an empty root-owned `0644` regular file, the model must be exactly MacBookAir9,1 and T2 detection must succeed. Invalid opt-in state, failed authorization or a missing/failed service never falls back to stock hibernation. Root invokes the fixed unit directly; an interactive terminal uses `sudo`, and a desktop caller uses `pkexec`. No command arguments can replace the unit, root or runtime path.

The provided `omarchy-t2-hibernate-product.service` must be installed separately as a root-owned unit. Its fixed executable is `/var/lib/omarchy/t2-hibernate-product/runtime/packages/t2-suspend/hibernate/product.py`, a reviewed root-owned snapshot, never the user-writable workspace or `$OMARCHY_PATH`. Before any attended service validation, deployment must supply the verified snapshot, private product configuration, truthful external qualified receipt, retained artifact/source pins and shared physical-cycle lock. The oneshot waits indefinitely through S4 and return verification; it has no automatic enablement, restart, retry or persistent successful-active state. Importing the code or installing the unit does not issue qualification.

Do not activate the opt-in marker yet: direct backend power writes do not provide logind's `PrepareForSleep` notifications or inhibitor handling, and the existing `omarchy-system-lock` exit status does not prove that the desktop is locked. Normal desktop activation requires a separately reviewed lock/inhibitor policy and attended normal-service validation. Initial attended root service validation must arrange and verify locking separately. The repository action-only menu change has no visual layout change; tests exercise routing without opening the menu or invoking a live power operation.

`bash test/shell.d/system-hibernate-test.sh` covers stock routing, root/terminal/desktop privilege selection, malformed opt-in state, exact model/T2 rejection, service failure propagation and fixed service/menu wiring using isolated command stubs.

### Next bounded desktop safety integration (design only)

The existing `omarchy-system-sleep-lock` requests the shell lock and polls `omarchy-shell lock status` until `.secure == true`, with bounded calls and a deadline. Reuse that helper for the requesting desktop session before admitting a routine invocation. Do not substitute `omarchy-system-lock`'s exit status, `lock isLocked`, a requested/pending flag or logind's advisory locked hint. A root-side gate must identify the actual active local graphical session and recheck that same session's secure shell status immediately before the image write; missing IPC, changed session or unsecured status must prevent power. Run any shell IPC as the session user, never privileged user-writable desktop code. Keep initial attended direct-service validation explicitly constrained and separately locked; it does not establish normal desktop sleep integration.

For normal desktop invocation, use a real logind Hibernate request, without force or inhibitor-bypass flags. A proposed root-owned conditional entry router would replace only `systemd-hibernate.service`'s `ExecStart`: absent opt-in runs the original `/usr/lib/systemd/systemd-sleep hibernate`; valid exact-host opt-in delegates to the fixed product snapshot and never falls back after an error. Preserve `hibernate.target`'s dependency on that service and the service's existing `sleep.target` ordering. Logind then owns block-inhibitor admission, delay-inhibitor waiting and genuine `PrepareForSleep(true/false)` notifications around its tracked target job, including a failed product job. Starting the custom service or a sleep target directly is not equivalent. Never synthesize logind signals or treat a one-time inhibitor listing as race-free authorization. See the installed systemd 261.2 login1/sleep manuals and [version-matched logind implementation](https://github.com/systemd/systemd/blob/v261/src/login/logind-dbus.c).

This router and secure-session gate are not implemented or deployed. The next patch should narrowly update the user command, add the root-owned entry router and conditional hibernate-service drop-in, and join the secure-session gate to the existing pre-power check. Stub tests must cover lock timeout/missing PAM/invalid status, session changes between admission and power, blocked logind requests, exact stock routing without opt-in, opted-in failure without a second power path, and target failure returning through logind cleanup. A disposable systemd/logind integration test must confirm genuine notification ordering and delay-inhibitor release/timeout before any attended physical validation. Replacing `systemd-sleep` also omits its user-slice freezing and local system-sleep hooks; inventory the installed hooks and explicitly decide compatibility rather than claiming the custom body preserves them. Keep the menu opt-in marker absent until these boundaries are reviewed and validated.
