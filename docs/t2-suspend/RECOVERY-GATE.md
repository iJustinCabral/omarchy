# MacBookAir9,1 cold-power recovery gate

This document defines the recovery conditions for a new hibernation diagnostic. It is not an authorization to run one. The current production boot has no `/dev/watchdog*` or `/sys/class/watchdog` device; `iTCO_wdt` reports that firmware prevents clearing `NO_REBOOT`. The NMI watchdog and EFI pstore do not provide a proven cold reset after a frozen hibernation path. A stock Limine default and a consumed one-shot protect the next boot selection, but neither can turn off a frozen laptop. An AC smart plug cannot reliably power-cycle a MacBook while its battery remains connected.

## Operator-attended non-S4 probes

The now-consumed `hibernate-efi-ftrace-marker/entry_probe.py` experiment targeted `pm_test=freezer` with disk mode `shutdown`. It neither wrote a hibernation image nor entered S4, but its ftrace callback invoked firmware `SetVariable` and could have hung. The operator accepted the possibility of another forced shutdown and remained at the machine. The exact one-use probe returned on stock boot `ef7a623b-53e4-4531-a6d6-5451182ed94c` with working built-in input; its stage-1 marker survived an orderly power-off to stock boot `f63b2683-afd8-4b7d-a3aa-bcdd4ff305d8` and was cleared under its exact-value protocol. The retained guard prohibits repetition. This history does not authorize a new freezer, image or S4 vector.

The runner requires a root-owned, private `recovery-acceptance.json` under `/var/lib/omarchy-t2-ftrace-entry-recovery/` before even prewriting EFI stage 0. The record identifies `ftrace-entry-freezer-recovery-acceptance-v1`, the source boot ID, the exact module and diagnostic-helper SHA-256 values, the production UKI and Limine SHA-256 values, `method: operator-attended-cold-power`, and `accepted: true`. This record is a boot-bound operator attestation, not proof that recovery would succeed. The runner does not create it automatically. A different boot, binary, method or withdrawn acceptance refuses arming and execution; the consumed `pm-attempted.json` remains terminal even if the record is rewritten.

If the freezer command returns, retain its result and check actual keyboard and trackpad events, radio state and PM-control restoration before any later reboot. If it hangs or the UI is unresponsive, the operator must force power off with the physical power button, then select the stock production entry if necessary. On the new boot, capture the boot ID, prior journal, one-use PM guard and exact EFI marker before cleanup. Do not rerun the same vector. A stage-1 marker after a forced shutdown shows only that the callback wrote the marker before the hang; its absence does not identify the failing function. Do not clear a marker unless the recorded source test returned successfully and the exact stage-1 value persisted on a different stock boot.

The distinct stock-kernel `run-efi-boundary.py` experiment is another operator-attended, non-S4 diagnostic. It uses `test_resume` only with a separately armed pre-write IPMODIFY abort that must redirect `swsusp_write()` to `-ECANCELED` before image I/O. Because failure to reach the hook could still hang and require physical power-off, its own `--operator-attended` flag, one-use durable PM guard, exact source boot and production hashes, AC, baseline swap header and hash-pinned modules are mandatory. If it hangs, preserve the EFI marker and guard on the next stock boot; stage 0/1/2 locates the last entered boundary but is not proof that the image completed. This does not authorize a retry of the consumed v11 diagnostic or real S4.

The one-use stock vector `ead9422f9c9e075613712ccf47730a70890f796969c6d7cfe3eb1e4c97ab49dc` returned with stage 2, one controlled abort and an unchanged swap-header page. Its `pm-attempted.json` guard is terminal. Exact-value cleanup removed only its disposable EFI variable after preserving the full bytes in `clear-intent.json`; all six root-owned evidence files remain. Do not run it again. This result establishes only that snapshot creation completed and image-writing entry was reached on that stock boot. It does not lift the independent-controller requirement for a real S4 attempt.

The distinct `hibernate-readback-ftrace/run-live-readback.py` diagnostic writes and reads an image in `test_resume` before a one-use `hibernation_restore()` abort; it does not enter S4. Its disposable guest qualified the hook sequence but not T2 hardware. A live run requires a newly prepared alternate Btrfs swapfile, original stock swap/header and boot command line unchanged, exact private modules, clean handoff, AC, and an operator physically able to force cold power off. Its guard is terminal from before alternate swapon, and a `pm-enter-intent.json` marks the narrower transition boundary. If the laptop hangs, use the physical power button and stock boot entry; the original command-line offset avoids the alternate image, but this is not proof of automatic recovery. Reconcile both headers, EFI marker, alternate swapfile and terminal guard on the returned stock boot before any cleanup or new vector. Do not repeat a failed image-I/O vector, and do not interpret a successful source-side readback as a cold S4 restoration.

The one-use Mac image-I/O vector `6701f3dfc5473a618c7b0411e650f1ea223b8d84c0eb3e0f4f351144763b90c8` returned with EFI stage 2, one controlled pre-atomic-restore abort, and kernel confirmation of successful image writing and reading. Its terminal PM guard must remain. On that source boot the stock offset was restored and both headers appeared normal, but `swapoff` of the alternate area timed out; the active file and exact stage-2 EFI variable were retained pending a different stock boot. This result narrows the remaining defect to atomic/cold restoration or T2 state after it; it does not lift the independent-controller gate for real S4.

An ordinary stock reboot released the alternate swap allocation without a same-boot `swapoff`; a read-only return audit bound the finalized but normally signed alternate header, exact EFI stage 2, production boot and inactive file. The exact cleanup then removed only the inactive temporary file and disposable EFI marker after fsynced intent, retaining the terminal guard and all other private evidence. No image-I/O retry or real S4 occurred during cleanup. The recovery gate for a new cold-S4 vector is unchanged.

## Autonomous S4 remains unqualified

The operator-attended record does not authorize a real S4 attempt. The offline `s4_backend.py` adapter can now bind an external EFI marker to a future pair vector while preserving the production kernel, but the pair runner refuses execution through it. Unattended S4 requires an independent controller that can actuate the laptop's physical power button without relying on the laptop's operating system, battery-powered AC adapter, network stack or firmware runtime services. Its power supply, control path, cold-reset action and stock-default return must first be demonstrated and recorded independently of a hibernation attempt. A durable source-stage marker has survived one operator-forced power-off, but not a write from within the failing S4 path. No independent controller or S4-path proof is currently recorded. Until those gates and a new, unconsumed S4 vector are established, keep all S4 attempts paused and preserve the historical guards.

The separate, one-use `forced_power_probe.py` tested EFI variable retention across an operator's physical long-press without invoking PM. On source boot `f63b2683-afd8-4b7d-a3aa-bcdd4ff305d8`, the root-owned arm and intent were fsynced, and the disposable `MBFP` variable read back with SHA-256 `c5a1dfb04df0b8e69717a8be2649ec8828fa5459ef85138871709808801b225c`. The source journal has no orderly shutdown after that readback; the operator reports holding the power button until off. Stock return boot `7e684644-8756-423b-b509-5504c220dee7` found the exact value, then exact-value cleanup removed only that variable. Five root-owned evidence files remain under `/var/lib/omarchy-t2-forced-power-probe/`. Software cannot independently prove the physical act, and this pass establishes only EFI storage retention for a normal-context write. Do not reuse the consumed probe or infer S4 safety or an autonomous reset from it.
